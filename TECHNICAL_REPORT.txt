1. EXECUTIVE SUMMARY
--------------------
AI CodeGuard is a locally deployable application intended to support secure
code review and debugging for ECU-oriented software. It combines heuristic
source-code checks, interpretation of supplied compiler/static-analysis/
runtime diagnostic logs, repository-aware question answering, code
summaries, and a workflow for reviewers to disposition findings.

The application uses a Streamlit interface and a FastAPI service. It
supports authentication, role-based and path-level repository permissions,
SQLite persistence, a local vector store, and an optional local language
model. The default retrieval embedder is a dependency-free lexical hashing
implementation. The optional language model is not required for
deterministic review.

The recorded offline evaluation reported 15 passing automated tests. A
single review of the demonstration repository scanned five files and
produced 17 findings. In a five-question retrieval check, two questions had
an exact top-ranked function citation and three had the expected file as
the top citation. This is a small exploratory evaluation, not a general
accuracy estimate. The project is heuristic, advisory, and not a claim of
MISRA compliance or certification.

2. INTRODUCTION
---------------
ECU software operates in embedded environments where reliability and
security are important. Software review may require considering source
code, coding guidance, build output, static-analysis messages, and runtime
diagnostics. Relating these sources and documenting review decisions can
be time-consuming.

AI CodeGuard was developed as a demonstration of a local assistant that
organizes this information and helps reviewers inspect potential issues.
It presents supporting context and allows authorized users to record
decisions. Automated and AI-generated results remain subject to human
verification.

3. PROBLEM AND PROJECT OBJECTIVES
---------------------------------
Problem:
Reviewers can face fragmented information when they must separately
inspect source code, diagnostics, and project guidance. A reported issue
may be difficult to assess if the location, evidence, explanation, or
review disposition is unclear.

Objectives:
1. Detect selected potential security, reliability, maintainability, and
   MISRA-oriented coding concerns in demonstration source.
2. Interpret example build, static-analysis, and sanitizer logs and map
   messages to source locations where possible.
3. Provide repository-aware answers with citations to retrieved source
   chunks.
4. Restrict analysis and retrieval according to a user's repository and
   path permissions.
5. Present structured findings and support a human review/disposition
   workflow.
6. Record audit events and expose basic review metrics and reports.
7. Evaluate the prototype with automated tests and a small, manually
   prepared retrieval question set.

4. REQUIREMENTS
---------------
Functional requirements:
- Authenticate users and apply roles to administrative and review actions.
- Register repositories and grant path-level allow/deny permissions.
- Review accessible source files using deterministic rules.
- Accept and interpret compiler and cppcheck output.
- Interpret runtime sanitizer/crash logs and identify candidate causes.
- Answer repository questions and provide retrieved-source citations.
- Summarize files/functions with structural metrics.
- List findings and permit authorized users to record dispositions.
- Export reports, publish accepted findings to an outbox, and view metrics.
- Optionally enrich results through an allow-listed local model endpoint.

Non-functional requirements and constraints:
- Support offline operation without a language model.
- Keep the default model integration local and restrict configured hosts.
- Exclude unauthorized paths before retrieval ranking.
- Preserve a review trail through audit entries and persistent storage.
- Treat rule and model output as advisory; do not auto-edit or auto-merge code.
- Keep the scope appropriate for a prototype rather than a certified
  production ECU verification system.

5. SYSTEM ARCHITECTURE
----------------------
The main components are:

1. Streamlit user interface
   Provides sign-in, repository selection, review, Ask, Debug, Summaries,
   Findings, and Metrics/Audit screens.

2. FastAPI application
   Exposes HTTP endpoints for authentication, repository administration,
   review, question answering, summaries, debugging, findings, metrics,
   publishing, and audit operations.

3. Services layer
   Manages users, password verification, repository registration, safe
   repository paths, path-level authorization, finding persistence, and
   review workflow operations.

4. Review engine
   Coordinates source-rule checks, compiler/cppcheck parsing, LLM
   enrichment when enabled, finding citations, question-answer retrieval,
   code summaries, and runtime-log debugging.

5. Rule and log analyzers
   The rule catalogue defines selected internal ICR checks. Log parsers
   process supported compiler, cppcheck XML, and sanitizer/crash formats.

6. Retrieval and persistence
   A NumPy cosine-similarity vector store persists indexed chunks. SQLite
   stores users, repositories, permissions, findings, and audit records.
   Application settings store generated data separately from sample source.

7. Optional local language model
   The LLM client supports Ollama and OpenAI-compatible local endpoints.
   LLM use is configurable; source checks and extractive retrieval can run
   without model inference.

High-level data flow:

User -> Streamlit UI -> FastAPI -> authorization -> review/retrieval
     -> structured response -> UI

For an optional model call:

Authorized context + trusted guideline excerpts
     -> prompt-safety wrapper -> configured local LLM
     -> output validation/screening -> response for human review

6. IMPLEMENTATION
-----------------
6.1 Authentication and authorization
Users are stored with salted PBKDF2-HMAC-SHA256 password hashes. Signed
tokens identify authenticated users. Roles include administrator,
reviewer, and developer. Repository path permissions support allow and
deny prefixes, with deny rules taking precedence. The service resolves
repository paths and rejects paths escaping the configured repository root.
Authorized-file filtering is applied to analysis and retrieval.

6.2 Source-code checks
The internal rule catalogue includes checks for selected patterns such as
dynamic memory use, unsafe string operations, goto, missing switch defaults,
unchecked allocation results, assignment in conditions, recursion,
inclusive array loop bounds, hard-coded credential-like values, weak random
generation, variable format strings, resource closure, unchecked numeric
conversion, complexity, and prompt-injection-like source text.

These checks are heuristic pattern-based analyses, not a full compiler
front-end. Findings have a rule identifier, severity, source location,
evidence, explanation/remediation fields, confidence, and references.
Inline deviation markers can suppress a matching rule at the relevant
location.

6.3 Diagnostic log interpretation
Compiler and cppcheck messages can be mapped to files/functions when their
paths correspond to authorized repository files. Runtime diagnostic
handling identifies supported sanitizer/crash patterns, attempts to
resolve source locations and functions, and can corroborate a log-derived
candidate with static findings.

6.4 Retrieval and repository Q&A
The default hash-768 embedder tokenizes identifiers and sub-words, hashes
features into vectors, and normalizes them. The vector store ranks chunks
using cosine similarity. A retarieval predicate filters metadata by user
authorization before ranking. The offline Ask mode returns relevant
authorized chunks with citations; it is extractive rather than a pretrained
language-model answer.

An optional SentenceTransformer embedder is available when configured with
a local model directory. It was not used in the recorded evaluation.

6.5 Optional LLM enrichment and prompt safety
The project configuration supports Ollama and OpenAI-compatible local
services. Compose sets the model tag to llama3.1:8b by default. The LLM
client sends requests to the configured endpoint and validates structured
JSON for finding enrichment. Repository content is wrapped as untrusted
input; output is screened before use.

The recorded evaluation did not use pretrained language-model inference.
An automated test uses a fake local Ollama-compatible HTTP server to test
the LLM path and rejection of unsafe content; this is a test double, not an
actual pretrained model. The configured model tag is not proof that the
model was installed or used, and an immutable model digest was not recorded.

6.6 Findings, audit, and reporting
Findings are persisted and de-duplicated using fingerprints. Authorized
reviewers can accept, reject, or leave findings open; developers can record
permitted dispositions. Rejection requires a comment. Accepted findings can
be written to a workflow outbox, with an optional allow-listed webhook.
Reports can be exported as Markdown. Audit records use a hash chain that
can be verified through the administrative endpoint.

8. SECURITY AND PRIVACY CONSIDERATIONS
--------------------------------------
The project includes controls intended to reduce selected risks:
- No model is required for offline deterministic checks.
- The LLM client enforces a configured host allow-list.
- Docker Compose separates services and places the API/Ollama on an internal
  network; the sample repository is mounted read-only.
- Repository access is checked at path level before retrieval and analysis.
- Source-like secrets are redacted in selected evidence paths.
- Repository content is treated as untrusted prompt input.
- Audit operations are recorded and the audit chain can be verified.
- The application does not automatically change source code or merge fixes.

These controls are not a production security certification. Authentication
is minimal, and production deployment would require an appropriate identity
provider, TLS, operational monitoring, and deployment-specific security
review. Generated databases, secret keys, and real credentials must not be
included in a public submission archive.

9. TESTING AND EVALUATION
-------------------------
9.1 Automated tests
The recorded command was:

  python -m pytest -q tests

Observed result:

  15 passed in 9.32s

The test suite exercises login rejection, seeded rule detection, evidence
redaction, inline deviations, path-level authorization, traversal
protection, prompt-injection defenses, compiler/cppcheck mapping, sanitizer
debugging, cited Q&A, summaries, finding dispositions, publishing, audit
integrity, metrics, host allow-listing, and LLM-path behavior using a fake
local server.

9.2 Offline review result
One isolated deterministic review scanned five source files and returned
17 findings:

  Critical: 2
  High:     5
  Medium:   7
  Low:      3

These are observed finding counts, not precision or recall. Because the
rules are heuristic, findings require manual validation.

9.3 Retrieval question set
Five manually authored questions were evaluated by checking the first
retrieval citation against an expected file and function:

  Top-1 exact file-and-function matches: 2/5 (40%)
  Top-1 expected-file matches:           3/5 (60%)

The questions and individual pass/fail citations are listed in
EVALUATION_EVIDENCE.txt. The small set is not statistically representative.
Observed ranking errors mean that citations should be verified by a human.

9.4 Sanitizer example
The supplied sample AddressSanitizer log was classified as a
global-buffer-overflow in CanRx_Store at src/can_rx.c:17. The system
identified the inclusive loop-bound finding ICR-008 at line 16 as
corroborating evidence, with observed root-cause confidence 0.70.
This checks interpretation of a supplied log; it does not claim the demo
program was compiled and executed in the evaluation.

9.5 Evaluation limitations
The study uses one synthetic repository, five source files, five
retrieval questions, and a small number of sample logs. No production data,
independently labelled benchmark, precision/recall measurement, statistical
test, or real pretrained-model evaluation was used. Results should be
described as a functional demonstration.

10. DEPLOYMENT AND OPERATION
----------------------------
The project can be run locally with the documented Python quick-start or
with Docker Compose. In Docker, the UI is exposed on port 8501 and the API
on port 8000 on the local machine. The API health endpoint reports the
selected backend and embedder. The root API path is not the health page;
the documented health endpoint is /health and API documentation is
available at /docs.

The Compose configuration includes an optional Ollama service. Starting
the API with an Ollama backend configured does not by itself start Ollama
or download the model. A model-based demonstration requires the service and
model to be available, and its exact model tag/digest and settings should
be recorded for reproducibility.

11. LIMITATIONS AND FUTURE WORK
-------------------------------
Current limitations:
- Pattern-based rules can miss defects and produce false positives.
- Retrieval ranking is imperfect, as shown by the small measured question
  set.
- The recorded results do not evaluate a pretrained LLM.
- The demonstration dataset is small and synthetic.
- The system does not provide certified MISRA compliance or safety proof.
- Production SSO and TLS are outside the current prototype scope.
- Git/PR diff review, SARIF export, and automated remediation are not
  implemented.

Potential future work:
- Expand the labelled question/answer and source-citation test set.
- Evaluate against additional approved repositories and log examples.
- Measure precision/recall using independent ground-truth labels.
- Run and document an optional local pretrained-model evaluation.
- Record model digest, prompt version, and inference settings.
- Improve code-aware chunking and retrieval ranking.
- Conduct usability and security reviews with representative users.

12. CONCLUSION
--------------
AI CodeGuard demonstrates a local, human-in-the-loop approach to ECU
software review and debugging. It combines deterministic checks, diagnostic
interpretation, authorized retrieval, structured findings, and reviewer
workflow. Recorded tests show that the implemented demonstration paths are
exercised, while retrieval mismatches and heuristic limitations show why
human validation remains necessary. Further evaluation on larger,
independently labelled datasets is required before making broader claims
about effectiveness.
